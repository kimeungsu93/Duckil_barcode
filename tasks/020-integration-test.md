# Task 020: 핵심 흐름 통합 E2E 테스트

> ROADMAP: `docs/ROADMAP.md` Phase 5 · Task 020
> 의존: Task 016, 017, 018, 019
> 상태: 완료 (2026-09-30)

## 개요

Task 017~019에서 API에 연결한 홈·상세·내보내기 화면의 테스트 체크리스트와, 스캔부터 내보내기까지의 통합 시나리오를 Playwright MCP로 실제 API에서 확인하고 결과를 기록한다. 모든 시나리오 뒤에는 `data/uploads/`의 파일과 DB의 사진 파일명이 정확히 일치해야 한다.

## 관련 파일

- 생성: `tests/fixtures/`(테스트 자료와 README), `scripts/check-data-integrity.ts`(정합성 검사, 커밋 1bcad60)
- 생성: `tasks/020-integration-test.md`(이 파일)
- 참고: `scripts/seed-export-test.ts`(대량·경계 데이터), `docs/ROADMAP.md` 추적표

## 테스트 환경

- 서버: 스크래치에 만든 프로젝트 복제본에서 `DATA_DIR=<스크래치>/data TZ=Asia/Seoul next dev --turbopack -p 3100`
  - 3000번 포트에 실데이터(`data/`)를 쓰는 기존 dev 서버가 떠 있어서 그대로 두고, `.next`가 겹치지 않도록 복제본에서 따로 띄웠다
- 브라우저: Playwright MCP(Chromium), 뷰포트 375x812(모바일 검사는 390x844 포함)
- 데이터: 기록은 `POST /api/records`로 만들고, 대량 데이터(201건, 501건)는 `seed-export-test.ts many`로 넣었다
- 서버 오류는 `page.route`로 해당 요청만 500 응답으로 가로챘다

- 직접 입력의 QR 원문란은 한 줄 입력이라 줄바꿈이 들어가지 않는다. 줄바꿈으로 구분된 원문(`PRODUCT:…\nLOT:…`)을 붙여 넣으면 구분자가 사라져 자동 입력이 되지 않는다. 카메라 인식 경로는 원문을 그대로 쓰므로 영향이 없고, 직접 입력에서는 `;`·`|`·`,` 구분자로 입력하면 된다. 실제 라벨 원문이 줄바꿈 형식이면 Task 021에서 입력란을 다시 검토한다
- 시작 바이트만 JPEG이고 내용이 깨진 파일은 서버가 받는다(ROADMAP Q8: 매직 바이트 검사). 정상 경로에서는 클라이언트 리사이즈가 디코딩에 실패해 업로드 전에 막힌다(오류 흐름 1). API로 직접 올린 경우에도 내보내기는 `200`으로 성공하고, 크기를 읽지 못한 사진은 기본 크기로 들어간다
- 상세 화면 S-상세-1(로딩)은 서버 컴포넌트에서 조회를 끝낸 뒤 렌더링하므로 실제 경로에서는 스켈레톤이 보일 틈이 없다. 화면 구성은 `?preview=loading`으로만 확인한다
